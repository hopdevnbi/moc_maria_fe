# Release updates and mobile logo recovery — 2026-10-13

The reported mobile screenshot already contains the latest hero text/layout but both remote logo images failed. This does not establish stale HTML as the cause. Live checks show homepage HTTP200 with `public, must-revalidate, max-age=0`, no service worker in the source, and Bunny image HTTP200 with a 30-day cache. The exact phone/CDN network error cannot be recovered from a screenshot.

Logo delivery now uses a content-hash CDN URL (`moc-maria-logo-c65b57b1d14d.webp`, uploaded before publication). `BrandLogo` automatically switches a failed CDN image to the existing same-origin transparent PNG, using a version query. This covers transient CDN failure, cached negative responses and WebP decoding issues without requiring customers to clear browser data. Existing CDN files remain intact. Future changed assets should receive their new content-hash URL; Next.js already versions CSS/JS chunks by content.

Every `npm run build` automatically embeds the Vercel commit SHA, GitHub SHA or local Git SHA as `NEXT_PUBLIC_RELEASE_ID`. Builds outside Git get a unique ID. The public `/api/release` waits for a request and forbids caching in browsers and shared CDNs. Public headers mount a small client watcher: checks once on load, every 60 seconds while visible and on return/focus/online. Hidden pages/offline checks do not interrupt use.

When a newer deployment is detected, idle public browsing pages reload after at least 15 seconds without interaction. Search/input/editable fields and selected form options block automatic reload. Chat, appointment, sign-in and private routes show an explicit “Cập nhật trang” action instead. A per-tab release guard prevents repeat automatic reload loops. Authentication cookies, local storage and draft contents are never cleared. The initial adoption requires customers with older code to reload/reopen once; an already-open pre-feature page cannot execute the new watcher remotely. Subsequent normal main releases require no manual cache action or separate purge job.

Validation covers failed-image fallback, cache headers, automatic idle public updates, protected routes, preserved text/rating, recent browsing activity, equal versions, offline return and reload-loop prevention. Production release evidence, exact test total, main SHA/CI and deployment are recorded in the own Plan/14_ACTIVE_WORK.json claim. No database, BE or existing shared services changed.
